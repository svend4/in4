🔴 Сценарий 2: Выход за пределы NVIDIA — AMD, Intel Arc, ARM Mali

Предыстория: зачем это нужно?

prima.cpp поддерживает только CUDA GPU (NVIDIA). Это значит, что AMD Radeon, Intel Arc, iGPU Strix Halo (59.4 ТФЛОПС RDNA 3.5), Mali G610 на Orange Pi — бесполезны как GPU-ускорители в prima.cpp. Но «ров CUDA» размывается одновременно с четырёх сторон: ZLUDA, SCALE, Claude Code и Vulkan.

Три пути: ZLUDA, SCALE и Claude Code (прямой порт)

ZLUDA

Что: Drop-in замена CUDA-библиотек. Переводит CUDA-вызовы в AMD ROCm/HIP без изменения кода приложения.

Автор: Andrzej Janik (изначально для Intel, потом AMD финансировал 2 года, потом бросил, теперь open-source с анонимным спонсором).

Статус (январь 2026):

• llama.cpp CUDA backend на ZLUDA — работает полностью
• Производительность «почти идентична» нативному ROCm
• Поддержка ROCm 7, Windows улучшена
• PyTorch — в разработке, ещё не готов
• 2 разработчика full-time

GPU: AMD RDNA 1/2/3 (RX 5700 XT → RX 7900 XTX)

SCALE

Что: «Чистая комната» — компилятор, который нативно компилирует CUDA-код для AMD GPU. Не слой трансляции, а полноценный компилятор, замена nvcc.

Кто: Spectral Compute (небольшая компания).

Статус (2026):

• Blender, llama.cpp, Hashcat, XGBoost — работают
• Тестирование на RDNA 2 и RDNA 3
• Базовое тестирование RDNA 1, разработка для Vega
• CDNA (серверные) — не поддерживаются
• Имитирует NVIDIA CUDA Toolkit

GPU: AMD RDNA 1/2/3 (потребительские)

🔥 Claude Code (прямой порт) — НОВИНКА января 2026

Что: Не трансляционный слой, а прямое переписывание CUDA-кода на ROCm/HIP с помощью AI-агента Claude Code (CLI-инструмент Anthropic с доступом к файловой системе и сборке).

Событие (январь 2026): Разработчик johnnytshi использовал Claude Code для портирования CUDA-бэкенда шахматного движка Leela Chess Zero (lc0) на ROCm. За 30 минут AI проанализировал зависимости, выявил несовместимые функции, написал wrappers — и код скомпилировался и запустился на AMD Instinct MI300X с производительностью, «практически идентичной нативной».

Ключевое отличие: Claude Code не просто заменяет cuda_ → hip_. Он анализирует логику ядер, находит несовместимости и пишет «мосты». Результат — нативный AMD-код, не трансляционный слой.

Источники: ITC.ua, GoHa.ru, Wccftech

Статус: Доказано на lc0 Не тестировано на prima.cpp

Побочный эффект: После этой новости Mac Mini M4 стали раскупаться ещё быстрее. Логика: если «ров CUDA» размывается → разработчики могут использовать Apple Silicon (Metal/MLX) без привязки к NVIDIA → Mac Mini становится ещё привлекательнее для локального AI. Хотя прямой связи между портом lc0 и продажами Mac нет, это отражает общий тренд ухода от CUDA-зависимости.
Юридический вопрос: Лицензия NVIDIA CUDA Toolkit запрещает использование для создания трансляционных слоёв для не-NVIDIA платформ. ZLUDA обходит через open-source. SCALE — «чистая комната». Claude Code — отдельная история: он пишет новый код, а не транслирует. Юридически это ближе к «чистой комнате» — человек (или AI) читает CUDA-код и пишет эквивалент на ROCm. NVIDIA сложнее оспорить этот подход.

🔧 Глубокое погружение: как портировать prima.cpp на Vulkan

Что вообще такое Vulkan (для тех кто не читал выше)

Vulkan — это не язык программирования и не фреймворк. Это стандарт (спецификация) — набор правил, описывающих, как программы должны общаться с видеокартой. Создан консорциумом Khronos Group (NVIDIA, AMD, Intel, ARM, Apple, Google, Samsung, Qualcomm — все вместе) в 2016 году.

Аналогия с розетками: Каждый производитель GPU сделал свой «разъём» — NVIDIA→CUDA, AMD→ROCm, Intel→SYCL, Apple→Metal. Vulkan — это универсальный переходник, который обязались поддерживать все производители. Один стандартный разъём → работает с любой видеокартой.

Код пишется на обычном C/C++, но GPU-вычисления выполняются через compute shaders — маленькие программы на языке GLSL, которые компилируются в промежуточный формат SPIR-V и отправляются на видеокарту через Vulkan API:

🔍 Как устроен Vulkan бэкенд в llama.cpp (уже существующий)

Vulkan бэкенд в llama.cpp — это ~15,000 строк C++ в директории ggml/src/ggml-vulkan/. Вот его структура:

Как работает конвейер вычислений

ШагЧто происходитГде в коде
1. Обнаружение GPUVulkan API сканирует все устройства: NVIDIA, AMD, Intel, Mali — все видныggml-vulkan.cpp: get_device_architecture()
2. Компиляция шейдеровПри сборке проекта ~30 GLSL файлов компилируются в SPIR-V байткод через glslc. Генерируются сотни вариантов для разных типов данных (F32, F16, Q4_0, Q4_K...)vulkan-shaders-gen.cpp: process_shaders()
3. Создание пайплайновДля каждой операции (matmul, softmax, add...) создаётся Vulkan Compute Pipeline с нужным шейдеромggml-vulkan.cpp: ggml_vk_create_pipeline()
4. Загрузка весовВеса модели копируются в GPU-память (device-local buffer) через staging bufferggml-vulkan.cpp: ggml_backend_vk_buffer_type()
5. Запись командДля каждого слоя нейросети записывается Command Buffer: «загрузи данные → вызови шейдер → сохрани результат»ggml-vulkan.cpp: ggml_vk_dispatch_pipeline()
6. ВыполнениеCommand Buffer отправляется в Compute Queue GPU. Драйвер переводит SPIR-V в машинный код конкретного GPUVulkan API: vkQueueSubmit()
7. СинхронизацияCPU ждёт завершения GPU через fence/semaphore, забирает результатVulkan API: vkWaitForFences()
Факт: Один и тот же SPIR-V байткод работает на NVIDIA RTX 4090, AMD RX 7900, Intel Arc A770 и ARM Mali G610 — каждый драйвер переводит его в свой машинный код. Именно поэтому Vulkan — «один ключ ко всем дверям».

🔬 Уровень 2: Как выглядит код — CUDA vs Vulkan бок о бок

Чтобы по-настоящему понять разницу, посмотрим на одну и ту же операцию — умножение матрицы на вектор (ключевая операция при генерации 1 токена) — в трёх представлениях:

Как это выглядит в CUDA (текущий prima.cpp)

Файл: ggml/src/ggml-cuda/mmv.cu

CUDA код (упрощённо)Что делает
// Ядро запускается на GPU
__global__ void mul_mat_vec_q4_0(
    const void * src0,   // матрица весов Q4_0
    const float * src1,  // входной вектор
    float * dst,         // результат
    int ncols, int nrows)
{
    // Каждый блок потоков обрабатывает
    // одну строку матрицы
    int row = blockIdx.x;
    
    // Деквантизация Q4_0 → float
    float val = dequantize_q4_0(src0, row, col);
    
    // Скалярное произведение строки × вектор
    float sum = 0.0f;
    for (int col = threadIdx.x; col < ncols;
         col += blockDim.x) {
        sum += val * src1[col];
    }
    
    // Параллельная редукция внутри warp
    sum = warpReduceSum(sum);
    
    // Записать результат
    if (threadIdx.x == 0) dst[row] = sum;
}
 Язык: CUDA C++ (.cu)

Компилятор: nvcc (только NVIDIA)

Запуск:
mul_mat_vec_q4_0<<<nrows, 256>>>(src0, src1, dst, ncols, nrows);

Работает на:
❌ Только NVIDIA GPU

Ключевые CUDA-специфики:
• __global__ — CUDA ключевое слово
• blockIdx.x — CUDA встроенная переменная
• threadIdx.x — CUDA встроенная переменная
• <<<grid, block>>> — CUDA синтаксис запуска

Как то же самое выглядит в Vulkan (уже в llama.cpp)

Файл: ggml/src/ggml-vulkan/vulkan-shaders/mul_mat_vec.comp

GLSL Compute Shader код (упрощённо)Что делает
#version 450
// Расширения для Vulkan
#extension GL_EXT_shader_16bit_storage : require

// Размер рабочей группы (аналог CUDA block)
layout(local_size_x = 32) in;

// Буферы данных (аналог CUDA указателей)
layout(binding = 0) readonly buffer A {
    uint8_t data_a[];  // матрица весов Q4_0
};
layout(binding = 1) readonly buffer B {
    B_TYPE data_b[];   // входной вектор
};
layout(binding = 2) writeonly buffer D {
    D_TYPE data_d[];   // результат
};

// Push-константы (аналог аргументов ядра)
layout(push_constant) uniform PushConstants {
    uint ncols;
    uint nrows;
};

void main() {
    // gl_GlobalInvocationID = CUDA аналог 
    // blockIdx * blockDim + threadIdx
    uint row = gl_WorkGroupID.x;
    uint tid = gl_LocalInvocationID.x;
    
    // Деквантизация Q4_0 → float
    // (та же математика, другой синтаксис)
    float val = dequantize_q4_0(data_a, row, col);
    
    float sum = 0.0;
    for (uint col = tid; col < ncols;
         col += gl_WorkGroupSize.x) {
        sum += val * float(data_b[col]);
    }
    
    // Параллельная редукция через subgroup
    // (аналог CUDA warp shuffle)
    sum = subgroupAdd(sum);
    
    if (tid == 0) data_d[row] = D_TYPE(sum);
}
 Язык: GLSL 4.50 (.comp)

Компилятор: glslc → SPIR-V (любой GPU)

Запуск:
vkCmdDispatch(cmd, nrows, 1, 1);

Работает на:
✅ NVIDIA ✅ AMD ✅ Intel ✅ Mali ✅ Adreno

Ключевые Vulkan-эквиваленты:
• layout(local_size_x) = blockDim.x
• gl_WorkGroupID.x = blockIdx.x
• gl_LocalInvocationID.x = threadIdx.x
• layout(binding=N) buffer = CUDA указатель
• subgroupAdd() = __shfl_xor_sync()
• vkCmdDispatch = <<<grid,block>>>
Главный вывод: Математика — идентичная. Разница только в синтаксисе обёртки. CUDA говорит threadIdx.x, Vulkan говорит gl_LocalInvocationID.x — а вычисление sum += val * vec[col] одно и то же. Именно поэтому Vulkan бэкенд достигает 70–90% производительности CUDA.

Halda — это алгоритм оптимального распределения нагрузки, решающий NP-трудную задачу. Он определяет: какие слои модели дать каждому устройству, и сколько из них считать на GPU vs CPU. Вот его внутренняя логика:

Но на генерации токенов (GEMV — матрица×вектор) разница меньше, потому что эта операция ограничена пропускной способностью памяти, а не вычислительной мощью.
Для prima.cpp это хорошая новость: prima.cpp оптимизирован для генерации токенов на слабых устройствах (70B модель на домашнем кластере). В этом режиме каждый узел обрабатывает 1 токен за раз → GEMV-операции → Vulkan теряет всего ~25% от CUDA, а не 60%. А на AMD/Intel/Mali Vulkan — это единственный путь к GPU, так что альтернативы нет.

ПроблемаОписаниеРешение
Subgroup size различается NVIDIA: 32, AMD: 64, Intel: 32, Mali: 16. Шейдеры, захардкоженные на warp=32, падают на Mali llama.cpp уже обрабатывает это: device->subgroup_size определяется при инициализации, шейдеры параметризованы
Cooperative Matrix не везде CoopMat (тензорные ядра через Vulkan) есть только на NVIDIA RTX, AMD RDNA3+. На Intel Arc, Mali — нет llama.cpp компилирует шейдеры и с CoopMat, и без. При запуске выбирает нужный вариант: device->coopmat_support ? pipeline_cm : pipeline_scalar
BF16 не везде BFloat16 поддержка есть только на новых GPU. Старые — только FP16 или FP32 llama.cpp проверяет GL_EXT_bfloat16 при сборке и генерирует шейдеры только если поддержка есть
UMA (Unified Memory) устройства iGPU (Intel Iris, AMD Radeon 680M, Mali) делят память с CPU. Нет отдельной VRAM llama.cpp детектирует UMA: device->uma = true. На UMA используется host-visible + device-local память (одно и то же физически). Halda должен учитывать: VRAM = часть RAM
Vulkan SDK версии Минимум Vulkan 1.2 для базовой работы, 1.3 для CoopMat2. Старые драйверы могут не поддерживать llama.cpp компилирует с --target-env=vulkan1.2 (базовые шейдеры) и vulkan1.3 (продвинутые). При запуске выбирает по возможностям драйвера
Android-специфика На Android Vulkan работает, но нужно NDK для компиляции, и есть баги с Mali GPU (segfault на некоторых моделях) prima.cpp уже поддерживает Android. Vulkan → нужен NDK toolchain с -DGGML_VULKAN=ON -DVK_USE_PLATFORM_ANDROID_KHR=ON
Halda не видит Vulkan GPU Если Halda ищет GPU только через cudaGetDeviceCount(), то на машине без NVIDIA он скажет «GPU нет» и будет считать всё на CPU Главная задача фазы 2: переписать обнаружение GPU через ggml абстракцию, которая видит все бэкенды
