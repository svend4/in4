01 Зачем портировать prima.cpp на Vulkan

Текущая проблема и стратегическое обоснование

Текущее состояние prima.cpp

Prima.cpp — первая распределённая система инференса для домашних кластеров. Она запускает 70B-модели (Llama 3, DeepSeek R1, QwQ-32B) на обычных устройствах через Wi-Fi. Но поддерживает только NVIDIA CUDA для GPU-ускорения.

GPU-ускорениеСтатус в prima.cpp% рынка GPU
NVIDIA CUDA✅ Работает~20% (дискретные)
AMD ROCm / Vulkan❌ Нет~12% (дискретные)
Intel Arc / Xe (SYCL / Vulkan)❌ Нет~3% (дискретные) + ~65% (iGPU)
Apple Metal❌ Нет~15% (macOS)
ARM Mali (Android)❌ Нет~45% (мобильные GPU)
Qualcomm Adreno (Android)❌ Нет~35% (мобильные GPU)
Проблема: ~80% GPU в мире не могут использовать prima.cpp для ускорения. Пользователи с AMD Radeon, Intel Arc, мобильными телефонами (Mali, Adreno) — вынуждены считать всё на CPU, теряя 5–50× производительности.

Почему именно Vulkan?

ПодходПокрытиеВремя разработкиОбслуживание
Vulkan (один раз)NVIDIA + AMD + Intel + Mali + Adreno + Android14–28 часов1× (один код)
ROCm (для AMD)Только AMD Radeon10–20 часов+1× (отдельный код)
SYCL (для Intel)Только Intel Arc/Xe10–20 часов+1× (отдельный код)
Metal (для Apple)Только macOS/iOS10–20 часов+1× (отдельный код)
OpenCL (устаревший)Широко, но медленно20–40 часов+1× (заброшен в llama.cpp)
Vulkan = пол (все получают GPU-ускорение), нативные бэкенды = потолок (максимум на выбранных платформах). Стратегия llama.cpp: сначала Vulkan для охвата всех, потом CUDA/Metal/SYCL для максимальной скорости на конкретных платформах.

Что получит prima.cpp после портирования

ВозможностьСейчас (CUDA only)После (+ Vulkan)
AMD Radeon RX 7900 XT❌ Только CPU → ~5 t/s на 7B✅ GPU → ~90 t/s на 7B
Intel Arc A770❌ Только CPU✅ GPU → ~35 t/s на 7B
Android телефон (Mali G710)❌ Только CPU → ~1 t/s✅ GPU → ~3–5 t/s (WIP)
Гетерогенный кластерCUDA + CPUCUDA + Vulkan + CPU (любые GPU вместе!)
Домашний кластер без NVIDIAВсе устройства на CPUКаждый GPU используется оптимально

Ключевой инсайт: Prima.cpp НЕ модифицировала GPU-бэкенды (Уровень 1). Все изменения — на верхних уровнях: PRP-кольцо, ZMQ, Halda, mmap/prefetch. Vulkan бэкенд уже существует в ggml. Портирование = подключение существующего кода + модификация Halda.

Что конкретно prima.cpp добавила к llama.cpp

КомпонентЧто делаетЗависит от GPU бэкенда?Нужно менять для Vulkan?
PRP (Piped-Ring Parallelism)Устройства образуют кольцо, каждое обрабатывает часть слоёв и передаёт результат следующему через ZMQ❌ Нет — передача через RAMНет
ZMQ сетевой слойПередача промежуточных тензоров между узлами по TCP/Wi-Fi❌ Нет — работает с RAM-буферамиНет
mmap загрузкаЛенивая загрузка весов модели с диска через memory-mapped файлы❌ Нет — это ОС-операцияНет
PrefetchПредзагрузка следующих слоёв пока текущие вычисляются⚠️ Частично — если prefetch вызывает CUDA API напрямуюВозможно
Halda (планировщик)Оптимальное распределение слоёв между CPU и GPU каждого устройства⚠️ Да — профилирование GPU, замер VRAMДА
Профилировщик устройствЗамер TFLOPS CPU/GPU, bandwidth, VRAM, дисковой скорости, сетевой задержки⚠️ Да — GPU-часть через CUDAДА
HiGHS LP-солверРешение задачи целочисленного линейного программирования (ILP) для Halda❌ Нет — чистая математикаНет
Makefile / система сборкиКомпиляция с флагом GGML_CUDA=1⚠️ Нужен новый флаг GGML_VULKAN=1ДА
Итого из 8 компонентов prima.cpp: 5 не требуют изменений, 1 возможно требует, 2 точно требуют. Основная работа — Halda-профилировщик и система сборки.

03 Что такое Vulkan бэкенд llama.cpp

Полная техническая карта того, что уже написано и работает

Структура файлов

Vulkan бэкенд находится в ggml/src/ggml-vulkan/ внутри llama.cpp:

ФайлСтрокНазначение
ggml-vulkan.cpp~12,000Ядро бэкенда: инициализация GPU, управление памятью, создание пайплайнов, диспетчеризация вычислений, реализация всех тензорных операций через Vulkan API
vulkan-shaders/mul_mm.comp~500Главный шейдер: матричное умножение (GEMM). Отвечает за ~90% вычислений нейросети. Поддерживает тайлинг, shared memory, CoopMat
vulkan-shaders/mul_mat_vec.comp~300Матрица × вектор (GEMV). Используется при генерации каждого нового токена (batch=1). Ограничен пропускной способностью памяти

vulkan-shaders/flash_attn*.comp~800Flash Attention — эффективный механизм внимания без квадратичного расхода памяти. 3 варианта: scalar, CoopMat1, CoopMat2

vulkan-shaders/rope_*.comp~200Rotary Position Embedding — кодирование позиций токенов
vulkan-shaders/norm.comp / rms_norm.comp~150Layer Normalization и RMS Normalization
vulkan-shaders/dequant_*.comp~400Деквантизация: Q4_0, Q4_1, Q5_0, Q5_1, Q8_0 → float16/float32
vulkan-shaders/types.comp / types.glsl~300Определения типов данных и функции деквантизации для K-квантов (Q2_K...Q6_K)
vulkan-shaders/dequant_funcs.glsl~200Функции деквантизации для use в mul_mat_vec: dequantize4() для SIMD-эффективных операций
vulkan-shaders/get_rows*.comp~100Embedding lookup: преобразование token_id → вектор
vulkan-shaders/copy_*.comp~100Копирование/конвертация данных между форматами (F32↔F16, transpose)

06 Конвейер компиляции шейдеров

Полная цепочка от исходного кода до исполнения на GPU

ЭТАП 1: Сборка проекта (cmake/make)

mul_mm.comp + defines → glslc → matmul_q4_0_f16_aligned.spv
mul_mat_vec.comp + defines → glslc → mul_mat_vec_q4_0_f32_f32.spv
soft_max.comp + defines → glslc → soft_max_f32.spv
... (~300 комбинаций) ...

ЭТАП 2: Встраивание в бинарник

~300 .spv файлов → vulkan-shaders-gen → ggml-vulkan-shaders.cpp
(SPIR-V байткод хранится как uint32_t массивы в C++ файле)

ЭТАП 3: Запуск программы (runtime)

uint32_t matmul_q4_0_data[] → vkCreateShaderModule() → VkShaderModule
VkShaderModule → vkCreateComputePipelines() → VkPipeline
(«ggml_vulkan: Compiling shaders....Done!» — это этот этап, 5–30 сек)

ЭТАП 4: Исполнение на GPU (JIT)

VkPipeline (SPIR-V) → Драйвер GPU → Нативный машинный код
(NVIDIA: SASS, AMD: ISA, Intel: EU code, Mali: bifrost code)

07 Код бок о бок: CUDA vs Vulkan

Одна операция в двух представлениях — чтобы увидеть что математика идентична

Операция: матрица × вектор с деквантизацией Q4_0

Это ключевая операция при генерации каждого токена. Матрица весов (квантизованная в Q4_0) умножается на входной вектор.

🟠 CUDA (ggml-cuda/mmv.cu)

// CUDA ядро для mul_mat_vec Q4_0
__global__ void mul_mat_vec_q4_0_f32(
    const void * __restrict__ src0,
    const float * __restrict__ src1,
    float * dst,
    int ncols, int nrows)
{
    int row = blockIdx.x;
    int tid = threadIdx.x;
    
    // Q4_0: 32 значения в блоке, 4 бита каждое
    float sum = 0.0f;
    for (int col = tid; col < ncols;
         col += blockDim.x) {
        // Деквантизация
        float val = dequantize_q4_0(
            src0, row, col);
        sum += val * src1[col];
    }
    
    // Warp-level reduction
    sum = warpReduceSum(sum);
    
    if (tid == 0) dst[row] = sum;
}

Запуск:
mul_mat_vec_q4_0_f32<<<nrows, 256>>>(...);
Работает: ❌ Только NVIDIA

🟢 Vulkan GLSL (vulkan-shaders/mul_mat_vec.comp)

// Vulkan compute shader для mul_mat_vec
#version 450
#extension GL_EXT_shader_16bit_storage
layout(local_size_x = 32) in;

layout(binding = 0) readonly buffer A {
    uint8_t data_a[]; // Q4_0 данные
};
layout(binding = 1) readonly buffer B {
    B_TYPE data_b[];  // входной вектор
};
layout(binding = 2) writeonly buffer D {
    D_TYPE data_d[];  // результат
};
layout(push_constant) uniform Params {
    uint ncols; uint nrows;
};

void main() {
    uint row = gl_WorkGroupID.x;
    uint tid = gl_LocalInvocationID.x;
    
    float sum = 0.0;
    for (uint col = tid; col < ncols;
         col += gl_WorkGroupSize.x) {
        float val = dequantize_q4_0(
            data_a, row, col);
        sum += val * float(data_b[col]);
    }
    
    // Subgroup reduction
    sum = subgroupAdd(sum);
    
    if (tid == 0) data_d[row] = D_TYPE(sum);
}

Запуск:
vkCmdDispatch(cmd, nrows, 1, 1);
Работает: ✅ NVIDIA, AMD, Intel, Mali, Adreno

Видите? Математика sum += val * vec[col] — абсолютно идентична. Только синтаксис обёртки различается. Это объясняет почему Vulkan достигает 70–90% от скорости CUDA: алгоритм тот же, overhead от абстракции минимален.

10 Фаза 2: Halda + Vulkan (ядро портирования)

Время: 4–8 часов. Самая критическая фаза — научить планировщик Halda работать с Vulkan GPU.

Что такое Halda и что он делает

Halda (Heterogeneity-Aware Layer-to-Device Allocation) — алгоритм, решающий NP-трудную задачу: распределить L слоёв модели между N устройствами, минимизируя время генерации одного токена (TPOT). На каждом устройстве слои могут считаться на CPU или GPU.

Входные данные Halda:
┌─────────────────────────┐ ┌─────────────────────────┐
│ Устройство 1 (Desktop) │ │ Устройство 2 (Laptop) │
│ CPU: 8.5 GFLOPS (F32) │ │ CPU: 4.2 GFLOPS (F32) │
│ GPU: 45.3 TFLOPS (CUDA) │ │ GPU: 12.1 TFLOPS (???) │
│ VRAM: 8 GB (RTX 3070) │ │ VRAM: 16 GB (Arc A770) │
│ RAM: 32 GB, SSD 3GB/s │ │ RAM: 16 GB, SSD 1GB/s │
│ Сеть: 1 Gbps Ethernet │ │ Сеть: 300 Mbps Wi-Fi │
└─────────────────────────┘ └─────────────────────────┘

Halda решает:
Устройство 1: 25 слоёв на GPU + 5 слоёв на CPU
Устройство 2: 20 слоёв на GPU + 10 слоёв на CPU
Раунды PRP: k=2 (каждый проходит через кольцо 2 раза)

→ Минимальный TPOT = 674 мс/токен для 70B модели

Текущая проблема: GPU = CUDA only

В текущей реализации Halda «GPU» означает «CUDA GPU». Если устройство 2 имеет Intel Arc A770, Halda скажет «GPU нет» и назначит все слои на CPU — теряя 5–10× производительности.

11 Фаза 3: PRP-кольцо и сетевой слой

Время: 2–4 часа. Проверить что PRP работает с Vulkan без изменений.

Как работает PRP (Piped-Ring Parallelism)

PRP кольцо для 70B модели (80 слоёв), 4 устройства, k=2:

Раунд 1: Раунд 2:
┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐
│ Dev1 │→│ Dev2 │→│ Dev3 │→│ Dev4 │→ │ Dev1 │→│ Dev2 │→│ Dev3 │→│ Dev4 │
│ L0-9 │ │L10-19│ │L20-29│ │L30-39│ │L40-49│ │L50-59│ │L60-69│ │L70-79│
└──────┘ └──────┘ └──────┘ └──────┘ └──────┘ └──────┘ └──────┘ └──────┘

Передача между узлами: hidden state tensor (~16 KB для batch=1)
Протокол: ZMQ TCP (через RAM, не через GPU)

GPU→RAM: vkMapMemory / cudaMemcpy D2H (уже в ggml)
RAM→ZMQ→RAM: zmq_send / zmq_recv (бэкенд-агностично)
RAM→GPU: staging buffer / cudaMemcpy H2D (уже в ggml)

Почему PRP НЕ нужно менять

Этап передачиЧто происходитЗависит от GPU бэкенда?
1. GPU → RAMРезультат вычисления слоя копируется из VRAM в RAM⚠️ Абстрагировано в ggml: ggml_backend_tensor_get() — работает для CUDA, Vulkan, Metal
2. RAM → СетьТензор отправляется через ZMQ по TCP/Wi-Fi❌ Нет — ZMQ работает с RAM-буферами
3. Сеть → RAMТензор получен на следующем устройстве❌ Нет — ZMQ кладёт в RAM
4. RAM → GPUТензор загружается в VRAM для следующего слоя⚠️ Абстрагировано в ggml: ggml_backend_tensor_set() — работает для всех
Вывод: PRP работает через RAM-буферы. ZMQ не знает и не должен знать откуда пришли данные — из CUDA VRAM или Vulkan VRAM. Функции ggml_backend_tensor_get() и ggml_backend_tensor_set() обрабатывают все бэкенды единообразно.

15 Подводные камни и edge cases

Потенциальные проблемы и их решения

ПроблемаОписаниеКак обнаружитьРешение
Subgroup size NVIDIA: 32, AMD: 64, Intel: 32, Mali: 16. Шейдеры, жёстко привязанные к warp=32, могут давать неправильные результаты на Mali Тест на Mali GPU + проверка device->subgroup_size ✅ Уже решено в llama.cpp: шейдеры параметризованы через gl_SubgroupSize
CoopMat недоступен Тензорные ядра через Vulkan (KHR_cooperative_matrix) есть только на NVIDIA RTX, AMD RDNA3+ device->coopmat_support при инициализации ✅ llama.cpp компилирует и CoopMat, и scalar варианты. При запуске выбирает по возможностям
UMA память iGPU делят RAM с CPU. Halda не должен суммировать RAM + VRAM device->uma == true В Halda: если UMA → total_memory = RAM, GPU использует часть
Vulkan SDK версия Минимум Vulkan 1.2. CoopMat2 требует 1.3. Старые драйверы не поддерживают vulkaninfo --summary llama.cpp компилирует шейдеры для 1.2 и 1.3, выбирает по драйверу
Android Mali segfault Некоторые модели/GPU комбинации на Android вызывают segfault Тестирование на конкретных устройствах WIP в llama.cpp. Обходной путь: уменьшить -ngl, использовать CPU-fallback
BF16 несовместимость BFloat16 есть только на новых GPU (RTX 40+, некоторые AMD) GL_EXT_bfloat16 проверяется при сборке Шейдеры с BF16 компилируются только если поддержка есть
Halda не видит Vulkan Если Halda ищет GPU только через cudaGetDeviceCount() grep CUDA в профилировщике Halda Фаза 2: заменить на ggml_backend абстракцию
Shader compilation timeout Первый запуск: 300–500 шейдеров компилируются → 5–30 секунд задержки «Compiling shaders.....Done!» в логах Нормальное поведение. Pipeline cache ускоряет последующие запуски
Multi-GPU Vulkan Несколько GPU на одной машине через Vulkan (не через PRP) GGML_VK_VISIBLE_DEVICES=0,1 llama.cpp поддерживает multi-GPU Vulkan с pipeline parallelism
Floating-point precision Vulkan и CUDA могут давать слегка разные результаты (порядок операций, rounding) Сравнение output при одинаковом seed Допустимо: разница в последних токенах. Perplexity должна быть ±0.5%

Архитектурный принцип: Если при добавлении Vulkan вы замените прямые CUDA вызовы в Halda на ggml абстракцию — то Metal, SYCL, WebGPU получатся автоматически без дополнительного кода в Halda. Они просто появятся как новые ggml_backend_dev и Halda увидит их через единый API.

Ключевой refactoring

// ВМЕСТО отдельных путей для каждого бэкенда:
#ifdef GGML_USE_CUDA
  ... cuda-specific code ...
#elif GGML_USE_VULKAN
  ... vulkan-specific code ...
#elif GGML_USE_METAL
  ... metal-specific code ...
#endif

// ИСПОЛЬЗУЙТЕ ggml абстракцию (один код для всех):
for (size_t i = 0; i < ggml_backend_reg_count(); i++) {
    auto reg = ggml_backend_reg_get(i);
    // Работает с CUDA, Vulkan, Metal, SYCL, WebGPU, CANN, MUSA...
    // Один и тот же код. Навсегда.
}

ВопросОтвет
Нужно ли писать GPU-шейдеры?НЕТ — все ~30 GLSL шейдеров (~15,000 строк) уже в llama.cpp
Нужно ли менять PRP (сетевой слой)?НЕТ — PRP работает через RAM-буферы, не зависит от GPU
Нужно ли менять ZMQ?НЕТ — ZMQ передаёт байты, не знает о GPU
Нужно ли менять mmap/prefetch?СКОРЕЕ НЕТ — если через ggml API. Проверить grep-ом
Нужно ли менять HiGHS LP-солвер?НЕТ — это чистая математика
Что ТОЧНО нужно менять?Makefile/CMake + Halda профилировщик (GPU detection, VRAM, TFLOPS)
