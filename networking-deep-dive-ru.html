1. Почему сеть — узкое место распределённого инференса

Генерация токенов в LLM — операция, ограниченная пропускной способностью памяти (memory-bandwidth bound). Каждый токен требует прочитать все веса модели из RAM. Но при распределённом инференсе появляется ещё одно ограничение — сеть.

Что передаётся по сети

При каждой генерации токена устройства должны обменяться промежуточными активациями (hidden states). Размер зависит от типа параллелизма:

Тип параллелизма Что передаётся Формула (байт на синхронизацию) Llama 70B (hidden=8192)
Pipeline (PP) Hidden state между сегментами hidden_size × 2 байта (FP16) 16 КБ
Tensor (TP) All-reduce после каждого слоя hidden_size × 2 × 2 (reduce-scatter + all-gather) 32 КБ × 80 слоёв = 2.5 МБ
PRP (prima.cpp) Hidden state при каждом ring-шаге hidden_size × 2 × k_оборотов 16 КБ × (N_устройств × k)

Расчёт сетевого overhead для Llama 70B

Pipeline Parallelism (4 узла): Синхронизаций на токен: 3 (между каждой парой) Данных на синхронизацию: 16 КБ Итого на токен: 48 КБ При 1 GbE (реально ~110 МБ/с): Передача: 48 КБ / 110 МБ/с = 0.44 мс Латентность TCP: ~300 мкс × 3 = 0.9 мс Итого сетевой overhead: ~1.3 мс на токен ← НЕЗНАЧИТЕЛЬНО НО! Pipeline bubble: 3 устройства простаивают пока 1 считает Если вычисление = 150 мс/сегмент → 3 × 150 = 450 мс простоя Итого: ~600 мс/токен → 1.7 tok/s (вместо теоретических 6.8) Tensor Parallelism (4 узла): All-reduce на слой: 32 КБ Слоёв: 80 Итого на токен: 2.5 МБ При 1 GbE (110 МБ/с): Передача: 2.5 МБ / 110 МБ/с = 22.7 мс Латентность: 300 мкс × 80 = 24 мс Итого: ~47 мс overhead × каждый токен При Thunderbolt 5 RDMA (5 ГБ/с, 3 мкс): Передача: 2.5 МБ / 5000 МБ/с = 0.5 мс Латентность: 3 мкс × 80 = 0.24 мс Итого: ~0.74 мс ← ПРАКТИЧЕСКИ БЕСПЛАТНО PRP (prima.cpp, 4 узла, k=2): Ring-шагов на токен: 4 × 2 = 8 Данных на шаг: 16 КБ Итого: 128 КБ При 1 GbE: Передача: 128 КБ / 110 МБ/с = 1.16 мс Латентность: 300 мкс × 8 = 2.4 мс Итого: ~3.6 мс — умеренный overhead + PRP перекрывает disk I/O, компенсируя overhead
Главный вывод:
- Pipeline parallelism: сеть не узкое место (48 КБ/токен), но pipeline bubble огромен
- Tensor parallelism: на 1 GbE — 47 мс overhead на токен. На TB5 RDMA — 0.74 мс. Разница в 63×!
- PRP: умеренный overhead (3.6 мс на 1 GbE), компенсируется перекрытием disk I/O
- Для tensor parallelism быстрая сеть критична. Для pipeline и PRP — менее важна.

Ключевое наблюдение: Латентность имеет большее значение, чем пропускная способность для tensor parallelism. 3. RDMA: что это и почему важно

RDMA (Remote Direct Memory Access) — технология, позволяющая одному компьютеру читать/писать память другого компьютера напрямую, без участия CPU и операционной системы удалённой машины.

Обычный TCP vs RDMA

Обычный TCP/IP (путь данных): Приложение → Системный вызов send() → Копирование в kernel buffer → → TCP/IP стек (заголовки, контрольные суммы) → Драйвер NIC → → NIC DMA → Провод → NIC DMA → → Драйвер NIC → Копирование из kernel buffer → Прерывание CPU → → Системный вызов recv() → Приложение Копирований памяти: 2–4 Переключений контекста: 4+ Участие CPU: на обеих сторонах Латентность: 100–500 мкс RDMA (путь данных): Приложение → ibv_post_send() → NIC DMA (из user-space напрямую!) → → Провод → NIC DMA (в память удалённого приложения напрямую!) → → Completion Queue уведомляет приложение Копирований памяти: 0 (zero-copy) Переключений контекста: 0 (kernel bypass) Участие CPU: минимальное (только на инициацию) Латентность: 1–5 мкс

Три типа RDMA

Тип Транспорт Латентность Требования Доступность для дома
InfiniBand RDMA InfiniBand (специальный протокол) 0.6–2 мкс InfiniBand HCA + IB свитч Б/у FDR — $100–300 за пару HCA + свитч
RoCE v2 Ethernet (UDP/IP) 2–10 мкс Mellanox ConnectX-4+ NIC + свитч с ECN/PFC Б/у 10–25G Mellanox — $50–150 за пару NIC
iWARP Ethernet (TCP/IP) 5–20 мкс iWARP NIC (Chelsio) Редко, малая экосистема
EXO RDMA (macOS) Thunderbolt 5 ~3 мкс Mac Mini M4 Pro + TB5 кабель $30–80 за кабель
EXO RDMA на Mac: Фреймворк EXO реализовал RDMA поверх Thunderbolt 5, используя технологию Apple IOPCIFamily для прямого доступа к памяти через TB5-контроллер. Это позволяет достичь ~3 мкс латентности и ~5 ГБ/с пропускной способности между Mac Mini M4 Pro — сравнимо с InfiniBand FDR. Именно поэтому кластер 4× Mac Mini + EXO даёт 32 tok/s на 70B.

Когда RDMA реально нужен

RDMA необходим:
- Tensor Parallelism (all-reduce на каждом слое)
- EXO на Mac-кластерах
- distributed-llama с быстрым интерконнектом
- Любой сценарий с >50 синхронизациями на токен
RDMA НЕ нужен:
- Pipeline Parallelism (llama.cpp RPC) — 3 синхронизации/токен
- PRP (prima.cpp) — умеренное количество
- Одиночный узел
- Модели <14B (не нужен кластер)

Шаг 4: Jumbo Frames (MTU 9000)

# Увеличение MTU снижает overhead заголовков TCP/IP # ВАЖНО: свитч тоже должен поддерживать jumbo frames! # Временно (до перезагрузки): sudo ip link set eth0 mtu 9000 # Постоянно (netplan): # В /etc/netplan/01-cluster.yaml добавить: # mtu: 9000 # Проверка: ping -M do -s 8972 10.0.0.2 # Если проходит — jumbo frames работают # Если "Message too long" — свитч не поддерживает
Эффект jumbo frames: MTU 1500 → MTU 9000 даёт +5–15% throughput за счёт меньшего числа пакетов. На TP-Link LS1008G jumbo frames не поддерживаются (неуправляемый свитч). Для jumbo frames нужен управляемый свитч (TP-Link TL-SG108E, ~$35).

Шаг 5: Бенчмарк iperf3

# На одном узле — сервер: iperf3 -s # На другом — клиент: iperf3 -c 10.0.0.2 -t 10 -P 4 # Ожидаемый результат для 1 GbE: # [SUM] 0.00-10.00 sec 1.10 GBytes 941 Mbits/sec # Латентность: ~0.3 мс (можно проверить через ping)

5. Пошаговая настройка: 2.5G / 5G / 10 GbE

2.5 GbE: самый доступный апгрейд

Многие современные мини-ПК (Orange Pi 5 Plus, Minisforum) уже имеют встроенный 2.5G порт (Realtek RTL8125). Нужен только 2.5G свитч.

# Проверить, какой NIC установлен: ethtool eth0 | grep Speed # Ожидание: Speed: 2500Mb/s # Если показывает 1000Mb/s — свитч ограничивает # Проверить link capabilities: ethtool eth0 | grep -i "supported link modes"

10 GbE: с б/у Mellanox ConnectX-3

Самый выгодный способ получить 10G — б/у карты Mellanox ConnectX-3 (MCX311A-XCAT). На eBay — $15–25 за штуку. Свитч б/у — $80–150.

6. Пошаговая настройка: Thunderbolt 5 (Mac кластер)

Топология: Daisy-chain

Mac Mini #1 ──TB5──► Mac Mini #2 ──TB5──► Mac Mini #3 ──TB5──► Mac Mini #4 (Master) (Worker 1) (Worker 2) (Worker 3) Каждый Mac Mini M4 Pro имеет 3× Thunderbolt 5 порта. TB5: 120 Гбит/с (80 Гбит/с симметричный, 120 Гбит/с асимметричный) Латентность: ~3 мкс (с RDMA через EXO)

Установить EXO: pip install exo-inference # 5. Запуск на каждом узле: # Mac Mini #1 (Master): exo run llama-3.1-70b --discovery-module manual \ --node-addresses 192.168.1.101,192.168.1.102,192.168.1.103 # Mac Mini #2–4 (Workers): exo join --master 192.168.1.100 # EXO автоматически определяет TB5 RDMA и использует его # вместо обычного TCP. Проверка: exo status # Должно показать: "Transport: RDMA (Thunderbolt 5)"
Требования для TB5 RDMA в EXO:
- macOS 15.0+ (Sequoia)
- Mac Mini M4 Pro или M4 Max (M4 базовый — только TB4)
- Кабели Thunderbolt 5 (USB4 v2 не даёт RDMA)
- EXO версии 0.5+ (с поддержкой RDMA)
- Не работает на Linux/Windows — только macOS

7. Пошаговая настройка: RoCE v2 (RDMA over Ethernet)

RoCE v2 позволяет получить RDMA-производительность поверх обычного Ethernet. Требуются Mellanox ConnectX-4+ и свитч с поддержкой ECN/PFC (Priority Flow Control).

Компонент Минимум Рекомендация Цена (б/у)
NIC Mellanox ConnectX-4 Lx (25G) ConnectX-5 (25/100G) $30–80
Свитч С поддержкой PFC/ECN Mellanox SN2100 или Arista 7050 $150–400 (б/у)
Кабели DAC SFP28 Passive DAC 1–3м $10–20

Загрузить модули: sudo modprobe mlx5_core sudo modprobe rdma_cm sudo modprobe rdma_ucm # 3. Проверить RDMA-устройства: ibv_devices # Ожидание: # device node GUID # ------ ---------------- # mlx5_0 248a07030012abcd # 4. Детали устройства: ibv_devinfo mlx5_0 # Должно показать: # transport: InfiniBand (0) или Ethernet (1) # active_mtu: 4096 # 5. Настроить RoCE v2 (GID index): # Проверить GID таблицу: cat /sys/class/infiniband/mlx5_0/ports/1/gids/0 # Должен быть IPv4 mapped адрес: 0000:0000:0000:0000:0000:ffff:0a0a:0001 # 6. Настроить PFC на свитче (зависит от модели): # Для Mellanox SN2100: # interface ethernet 1/1 # priority-flow-control mode on # traffic-class 3 congestion-control ecn minimum-absolute 150 # # Без PFC — RoCE v2 работает, но при congestion возможны потери # 7. Бенчмарк RDMA: # Сервер: ib_write_bw -d mlx5_0 -F --report_gbits # Клиент: ib_write_bw -d mlx5_0 -F --report_gbits 10.10.0.1 # Ожидание (25 GbE): # BW peak[Gb/sec]: 23.8 # BW average[Gb/sec]: 23.5 # Латентность: # Сервер: ib_write_lat -d mlx5_0 # Клиент: ib_write_lat -d mlx5_0 10.10.0.1 # Ожидание: ~2-5 мкс
Важно: RoCE v2 по-настоящему полезен, только если ваш AI-фреймворк поддерживает RDMA. Из домашних фреймворков: EXO (Mac TB5 RDMA), NCCL (для PyTorch). llama.cpp, prima.cpp, distributed-llama — используют TCP-сокеты, даже если RDMA доступен. Для этих фреймворков RoCE v2 не даёт преимущества.

8. Топологии сети для кластеров

Star (Звезда) — через коммутатор

┌──────────┐ │ Switch │ └─┬──┬──┬─┘ │ │ │ ┌────┘ │ └────┐ D1 D2 D3 Плюсы: простота, любое количество узлов Минусы: свитч — единая точка отказа, общий bandwidth Для кого: llama.cpp RPC, distributed-llama, prima.cpp Стоимость: свитч $15–200 (зависит от скорости)

Daisy-chain (Цепочка)

D1 ──── D2 ──── D3 ──── D4 Плюсы: нет свитча, низкая латентность между соседями Минусы: D1→D4 = 3 хопа, общая латентность растёт Для кого: Thunderbolt 5 (Mac кластер + EXO) Стоимость: только кабели ($30–80 каждый)

Ring (Кольцо) — для PRP

D1 ──── D2 │ │ D4 ──── D3 Плюсы: каждый узел имеет 2 соседей, параллельные пути Минусы: нужно 2 NIC на узел (или свитч с LACP) Для кого: prima.cpp PRP (native ring topology) Стоимость: 2× NIC на узел или 1 свитч

Full Mesh (Полная сетка)

D1 ──── D2 │ ╲ ╱ │ │ ╲ ╱ │ │ ╲ ╱ │ │ ╳ │ │ ╱ ╲ │ │ ╱ ╲ │ D4 ──── D3 Плюсы: прямое соединение между любой парой, отказоустойчивость Минусы: N×(N-1)/2 соединений, сложная настройка Для кого: малые кластеры (4 узла), TB5 (3 порта на Mac Mini) Стоимость: много кабелей, но нет свитча
Рекомендация по топологии:
- 2–4 узла, Ethernet → Star (звезда) через свитч. Просто и надёжно.
- 2–4 узла, Thunderbolt 5 → Daisy-chain или mesh (Mac Mini).
- 4 узла, prima.cpp → Star через свитч (prima.cpp сама формирует ring поверх).
- 8+ узлов → Star с управляемым свитчом + VLAN для изоляции трафика.

9. Оптимизация TCP для AI-трафика

Все основные фреймворки (llama.cpp RPC, prima.cpp, distributed-llama) используют TCP-сокеты. Правильная настройка TCP может дать +10–30% throughput и -30–50% латентности.

Sysctl параметры

# /etc/sysctl.d/99-ai-cluster.conf # === Буферы сокетов === # Увеличиваем максимальный размер буферов (по умолчанию ~208 КБ) net.core.rmem_max = 67108864 # 64 МБ net.core.wmem_max = 67108864 # 64 МБ net.core.rmem_default = 1048576 # 1 МБ net.core.wmem_default = 1048576 # 1 МБ # TCP auto-tuning буферы (мин, по-умолчанию, макс) net.ipv4.tcp_rmem = 4096 1048576 67108864 net.ipv4.tcp_wmem = 4096 1048576 67108864 # === Очередь === net.core.netdev_max_backlog = 30000 # Очередь входящих пакетов net.core.somaxconn = 65535 # Макс. соединений в очереди # === TCP параметры === net.ipv4.tcp_no_metrics_save = 1 # Не кешировать метрики net.ipv4.tcp_moderate_rcvbuf = 1 # Авто-подстройка буферов net.ipv4.tcp_window_scaling = 1 # Масштабирование окна TCP net.ipv4.tcp_timestamps = 1 # Для точного RTT net.ipv4.tcp_sack = 1 # Selective ACK # === Уменьшение латентности === net.ipv4.tcp_low_latency = 1 # Приоритет латентности net.ipv4.tcp_fastopen = 3 # TCP Fast Open (клиент+сервер) # Применить: # sudo sysctl -p /etc/sysctl.d/99-ai-cluster.conf

TCP_NODELAY и TCP_QUICKACK

# TCP_NODELAY отключает алгоритм Nagle — отправляет данные сразу, # без ожидания заполнения пакета. Критично для AI-инференса! # # В коде (C/C++): # int flag = 1; # setsockopt(sock, IPPROTO_TCP, TCP_NODELAY, &flag, sizeof(flag)); # # distributed-llama и prima.cpp УЖЕ используют TCP_NODELAY. # llama.cpp RPC — тоже. # # TCP_QUICKACK отправляет ACK немедленно (без delayed ACK): # setsockopt(sock, IPPROTO_TCP, TCP_QUICKACK, &flag, sizeof(flag)); # Нужно устанавливать после каждого recv() — не sticky.

IRQ Affinity и CPU Pinning

# Привязать прерывания NIC к определённым CPU ядрам # чтобы избежать конкуренции с AI-вычислениями # Найти IRQ вашего NIC: cat /proc/interrupts | grep eth0 # Например: 45: ... eth0-TxRx-0 # Привязать IRQ 45 к CPU 0: echo 1 > /proc/irq/45/smp_affinity # Для мульти-очередных NIC (10G+): # Установить irqbalance: sudo apt install irqbalance # Или вручную через set_irq_affinity.sh (из Mellanox tools)

Ring Buffer и Coalescing

# Увеличить ring buffer NIC: sudo ethtool -G eth0 rx 4096 tx 4096 # Настроить interrupt coalescing (баланс throughput/latency): # Для НИЗКОЙ ЛАТЕНТНОСТИ (AI-инференс): sudo ethtool -C eth0 rx-usecs 0 tx-usecs 0 rx-frames 1 tx-frames 1 # Для ВЫСОКОГО THROUGHPUT (передача больших моделей): sudo ethtool -C eth0 rx-usecs 50 tx-usecs 50 rx-frames 64 tx-frames 64 # Проверить текущие настройки: ethtool -c eth0 ethtool -g eth0
Результат TCP-оптимизации:
- 1 GbE: 940 Мбит/с → 941 Мбит/с (потолок почти достигнут — мало что можно улучшить)
- 10 GbE: 8.5 → 9.3 Гбит/с (+10%) с правильными буферами
- Латентность: 300 мкс → 150–200 мкс с TCP_NODELAY + coalescing=0
- Главный эффект: не throughput, а снижение jitter (дрожания). Стабильная латентность важнее средней.

11. Расчёт пропускной способности для каждой модели

Формулы

Pipeline Parallelism (PP): Данных на токен = hidden_size × 2 байта × (N_узлов - 1) Где hidden_size: Llama 8B=4096, 70B=8192, 405B=16384 Tensor Parallelism (TP): Данных на токен = hidden_size × 2 × 2 × num_layers (all-reduce = reduce-scatter + all-gather на каждом слое) PRP (prima.cpp): Данных на токен = hidden_size × 2 × N_узлов × k_оборотов k обычно = 2 для моделей 60B+

Формула: tok/s с учётом сетевого overhead

Реальные tok/s = 1 / (T_compute + T_network + T_sync) Где: T_compute = model_size_bytes / (memory_bandwidth × num_devices) T_network = data_per_token / network_throughput + num_syncs × latency T_sync = overhead синхронизации (barrier, etc.) Пример: Llama 70B Q4_K_M (40 ГБ), 4 узла, 1 GbE llama.cpp RPC (Pipeline): T_compute = 40 ГБ / 273 ГБ/с = 146 мс (на самом медленном узле) T_pipeline_bubble = 146 × 3 = 438 мс (3 узла простаивают) T_network = 1.3 мс (незначительно) Итого: ~585 мс → 1.7 tok/s Сеть: 0.2% от общего времени — не bottleneck distributed-llama (Tensor Parallel): T_compute = 40 ГБ / (4 × 34 ГБ/с) = 294 мс (Pi 5, 34 ГБ/с каждый) T_network = 47 мс (all-reduce через 1 GbE) Итого: ~341 мс → 2.9 tok/s Сеть: 14% от общего времени — заметно! С 10 GbE: 294 + 6 = 300 мс → 3.3 tok/s (+14%) prima.cpp PRP: T_compute = 40 ГБ / (4 × memory_bw) — распределено T_network = 3.5 мс T_disk_prefetch = перекрывается (скрытая) Итого зависит от конфигурации — 500–700 мс → 1.4–2 tok/s Сеть: 0.5–0.7% — не bottleneck

14. Типичные проблемы и диагностика

Проблема Симптомы Диагностика Решение
MTU mismatch Пинг работает, но большие пакеты теряются. iperf3 показывает 100 Мбит/с вместо 1 Гбит/с ping -M do -s 8972 10.0.0.2 — если не проходит, MTU не совпадает Установить одинаковый MTU на всех узлах и свитче
Кабель Cat5e на 2.5G Линк поднимается на 1G вместо 2.5G ethtool eth0 | grep Speed Использовать Cat6 или Cat6a. Cat5e ненадёжен на 2.5G+ при длине >5м
IRQ storm на 10G CPU загружен на 100% одним ядром при высоком трафике cat /proc/interrupts | grep mlx — все прерывания на одном CPU Настроить irq affinity: set_irq_affinity_bynode.sh 0 mlx5_0
TCP window too small 10 GbE даёт только 2–3 Гбит/с ss -t -i | grep wscale Увеличить net.ipv4.tcp_rmem и tcp_wmem
RoCE не работает ibv_devices не показывает устройство lspci | grep Mellanox + dmesg | grep mlx Загрузить модули: modprobe mlx5_core. Установить rdma-core
Wi-Fi interference Скорость плавает 100–600 Мбит/с iwconfig wlan0 — проверить SNR и канал Использовать 5 ГГц (DFS каналы), Wi-Fi 6E (6 ГГц) или перейти на Ethernet
Switch buffer overflow Потери пакетов при burst-трафике (all-reduce) ethtool -S eth0 | grep drop Управляемый свитч с ECN/PFC. Или свитч с большим буфером (MikroTik)
Высокий jitter tok/s нестабильный, прыгает ±50% ping -c 100 10.0.0.2 | tail -1 — смотреть mdev Отключить power saving на NIC: ethtool -s eth0 wol d. Отключить C-states в BIOS
