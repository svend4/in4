⚡ prima.cpp — прорыв для домашних кластеров мини-ПК

Распределённый LLM-инференс нового поколения: Piped-Ring Parallelism, Halda, disk offloading

Часть 6 серии исследований. Февраль 2026. Источник: arXiv:2504.08791 (Li et al.), GitHub: Lizonghang/prima.cpp

Что такое prima.cpp? Это распределённая реализация llama.cpp, которая позволяет запускать модели 30B–70B на кластере из обычных домашних устройств — ноутбуков, десктопов, телефонов, мини-ПК. Ключевое отличие от всех предыдущих решений (llama.cpp RPC, EXO, distributed-llama): prima.cpp не требует, чтобы модель целиком помещалась в RAM кластера. Она использует disk offloading через mmap и новый тип параллелизма — Piped-Ring Parallelism (PRP), который скрывает задержки чтения с диска. Результат: 70B модель на кластере из слабых устройств с 37 ГБ суммарной RAM → 674 мс/токен (1.48 tok/s). Со speculative decoding: 32B → 26 tok/s, 70B → ~2 tok/s.

1. 🆕 Что принципиально нового приносит prima.cpp

Все предыдущие фреймворки (llama.cpp RPC, EXO, distributed-llama) имеют общую проблему: суммарная RAM кластера должна быть ≥ размера модели. Модель 70B в Q4 весит ~40 ГБ → нужен кластер с ≥ 40 ГБ свободной RAM. Если не хватает — модель не запустится или всё рухнет.

prima.cpp ломает это ограничение. Три инновации:

1. Disk Offloading через mmap

Веса модели загружаются лениво через mmap. ОС сама управляет page cache — загружает нужные слои с NVMe SSD когда нужно, выгружает когда память нужна другим приложениям. Модель любого размера можно запустить даже на устройстве с 2 ГБ RAM, если есть быстрый диск.

Memory pressure < 6% — можно одновременно смотреть YouTube, пока идёт инференс.

2. Piped-Ring Parallelism (PRP)

Новый тип параллелизма — не pipeline (цепочка), не tensor (разрезание тензоров), а кольцо: устройства передают результаты по кругу, делая несколько оборотов для генерации одного токена. С prefetching — пока устройство A считает, устройство B подгружает следующие слои с диска. Задержки чтения с диска скрываются за вычислениями других устройств.

3. Halda — умный планировщик

Алгоритм, который решает NP-трудную задачу: сколько слоёв модели дать каждому устройству, что на GPU, что на CPU, что на диск. Учитывает:

— Скорость CPU и GPU каждого устройства
— Доступную RAM и VRAM
— Скорость чтения SSD/HDD
— Пропускную способность и латентность сети
— Особенности ОС (macOS vs Linux vs Android)

Использует HiGHS ILP solver (линейная оптимизация) для нахождения оптимума.

4. Гетерогенность

prima.cpp — первый фреймворк, который нормально работает с разнородным железом. В кластере могут быть одновременно:

— Mac M1 (macOS, Metal GPU)
— Ноутбук с RTX 3070 (Linux, CUDA)
— Десктоп с RTX 2080 Ti (Linux, CUDA)
— Телефон Huawei Mate 40 Pro (Termux)
— Мини-ПК без GPU (CPU-only)

Halda автоматически определяет возможности каждого устройства и распределяет нагрузку оптимально.

2. 🔧 Архитектура prima.cpp: как работает PRP

Сравнение типов параллелизма

Параллелизм Как работает Кто использует Проблема
Pipeline (PP) Модель разрезается на сегменты, каждое устройство обрабатывает свой сегмент последовательно llama.cpp RPC, EXO (на Linux) Одно устройство работает, остальные простаивают (pipeline bubbles). Нужно чтобы модель влезла в RAM
Tensor (TP) Тензоры внутри каждого слоя разрезаются между устройствами, all-reduce после каждого слоя distributed-llama, EXO (на macOS), NVIDIA NVLink Требует быстрый интерконнект (<10 мкс). На Wi-Fi/Ethernet — катастрофические задержки all-reduce
Sequential (SP) Устройства обрабатывают модель по очереди, каждое — полный проход TPI-LLM Очень медленно — нет параллелизма
Piped-Ring (PRP) ← НОВЫЙ Устройства в кольце. Каждое обрабатывает часть слоёв и передаёт результат следующему. Несколько оборотов за токен. Prefetching перекрывает disk I/O prima.cpp Overhead от нескольких оборотов, но компенсируется скрытием disk latency

Визуализация PRP (Piped-Ring Parallelism)

Классический Pipeline Parallelism (PP): D1 → D2 → D3 → D4 (1 проход = 1 токен) [20 слоёв] [20] [20] [20] Проблема: если D1 читает с диска = все ждут! Piped-Ring Parallelism (PRP): D1 → D2 → D3 → D4 → D1 → D2 → D3 → D4 (k=2 оборота = 1 токен) [10 слоёв] [10] [10] [10] [10] [10] [10] [10] Время: ─────────────────────────────────────────► D1: [compute 10 layers] [prefetch] ─── [compute 10 layers] [prefetch] D2: ── [prefetch] [compute 10 layers] ── [prefetch] [compute 10 layers] D3: ─── [prefetch] [compute 10 layers] ── [prefetch] [compute 10 layers] D4: ──── [prefetch] [compute 10 layers] ── [prefetch] [compute 10 layers] ↑ Пока D2 считает, D3 подгружает с SSD — disk latency СКРЫВАЕТСЯ!
Ключевая идея PRP: При k=1 (один оборот) — это обычный pipeline, и prefetching бесполезен из-за «prefetch-release конфликта» (OS выгружает предзагруженные страницы). При k≥2 каждое устройство обрабатывает меньше слоёв за оборот, но делает больше оборотов. Это создаёт окно для prefetch следующих слоёв, пока другие устройства работают. На моделях >60B, где disk offloading неизбежен, PRP снижает латентность почти вдвое по сравнению с PP.

Halda: как распределяются слои

Пример распределения для Llama 3-70B (80 слоёв, Q4K) на тестовом кластере:

Halda решает: какие слои куда, сколько на GPU, сколько на CPU, сколько с диска Устройство │ CPU слои │ GPU слои │ С диска │ Почему ────────────┼──────────┼──────────┼─────────┼─────────────────────────── D1 (Mac M1) │ 5 │ 4 │ mmap │ Metal GPU слабее CUDA, но помогает D2 (3070) │ 0 │ 10 │ 0 │ 8 ГБ VRAM → 10 слоёв целиком в GPU D3 (2080Ti) │ 2 │ 13 │ mmap │ 11 ГБ VRAM + быстрый SSD 3.17 ГБ/с D4 (телефон)│ 3 │ 0 │ mmap │ Только CPU, медленный диск 1.37 ГБ/с ────────────┼──────────┼──────────┼─────────┤ Итого: │ 10 │ 27 │ +43 │ = 80 слоёв. Только 37 слоёв в RAM/VRAM!

Halda автоматически выбирает даже количество устройств. Для малых моделей (<14B) он определяет, что D3 одна справится лучше всего → использует только её. «Больше устройств ≠ быстрее» — Halda это понимает.

🔴 Критическое ограничение: GPU поддержка

prima.cpp сейчас поддерживает только CUDA GPU (NVIDIA).

Это означает:
• Мини-ПК без GPU (большинство!) → работает только на CPU. prima.cpp всё равно быстрее llama.cpp благодаря PRP и Halda, но без GPU-ускорения.
• AMD GPU (Strix Halo, Radeon) → ❌ НЕ поддерживается. Vulkan «в роадмапе», но не реализован.
• Intel Arc GPU → ❌ НЕ поддерживается.
• Apple Metal → ✅ Поддерживается, но авторы отмечают, что эффективность «значительно ниже» CUDA.
• Mac Mini M4 / M4 Pro → ✅ Работает через Metal, но Apple Silicon в prima.cpp медленнее, чем в нативном llama.cpp (Metal оптимизации llama.cpp более зрелые).

Для кластеров мини-ПК без NVIDIA GPU — prima.cpp работает в CPU-only режиме. Это всё ещё лучше, чем llama.cpp RPC на больших моделях, благодаря PRP и disk offloading.

Какие мини-ПК лучше всего подходят для prima.cpp

Mac Mini M4 Pro Apple Silicon, 14 ядер 64 ГБ Metal (работает, но медленнее CUDA) ~7 ГБ/с Хорошо, Metal не идеально

Б/у десктоп с RTX 2080Ti/3070 i7/i9 или Ryzen 32–64 ГБ CUDA ✅ NVMe Лучший $/perf!
Парадокс prima.cpp для мини-ПК: Фреймворк лучше всего работает с NVIDIA GPU, но большинство мини-ПК (Strix Halo, Mac Mini, Intel NUC) не имеют NVIDIA GPU. Два выхода:
1. Ждать Vulkan-поддержку (тогда AMD/Intel GPU заработают)
2. Использовать prima.cpp в CPU-only режиме — всё равно выигрывает у llama.cpp на моделях 30B+ благодаря PRP + disk offloading
3. Строить кластер из б/у десктопов с NVIDIA GPU — самый эффективный вариант для prima.cpp сейчас

6. 💡 Конкретные сценарии для мини-ПК кластеров

Сценарий A: «Чистый CPU» — 4× Framework Desktop (Strix Halo)

Кластер: 4× Framework Desktop (Strix Halo, 128 ГБ LPDDR5X) Сеть: 10 GbE (USB4v2 или PCIe NIC) Суммарная RAM: 512 ГБ SSD: PCIe 5.0, 10+ ГБ/с на узел GPU: ❌ (AMD iGPU не поддерж. prima.cpp) prima.cpp CPU-only + PRP: • 70B Q4K (~40 ГБ) → полностью в RAM одного узла, Halda → 1 узел → Скорость ≈ llama.cpp на одном узле ≈ 4–5 tok/s → prima.cpp НЕ даёт преимущества (модель влезает) • 405B Q4K (~230 ГБ) → НЕ влезает на 1 узел → prima.cpp распределяет на 2–3 узла → PRP + disk offloading → оценка: 0.3–1 tok/s (CPU-only, но с перекрытием disk I/O) → llama.cpp RPC на том же кластере: ~0.1–0.3 tok/s → prima.cpp: 2–3× быстрее • DeepSeek V3 671B Q4K (~380 ГБ) → все 4 узла → PRP + prefetching → оценка: 0.1–0.5 tok/s → БЕЗ prima.cpp: практически невозможно на CPU-only кластере
Вывод по Strix Halo: prima.cpp полезна здесь только для моделей, которые не влезают в RAM одного узла. Для моделей ≤128 ГБ (70B, Qwen3-235B в Q4) — один Framework Desktop с llama.cpp нативно будет быстрее. prima.cpp начинает выигрывать на моделях 200B+.

Сценарий B: «GPU кластер» — гетерогенные устройства с NVIDIA

Кластер: D1: Мини-ПК с RTX 4060 Ti (16 ГБ VRAM, 32 ГБ RAM) $800 D2: Б/у десктоп с RTX 3070 (8 ГБ VRAM, 32 ГБ RAM) $400 D3: Б/у десктоп с RTX 2080 Ti (11 ГБ VRAM, 64 ГБ RAM) $350 D4: Старый ноутбук (CPU-only, 16 ГБ RAM) $0 (уже есть) Сеть: Gigabit Ethernet Итого: ~$1 550, суммарно 35 ГБ VRAM + 144 ГБ RAM prima.cpp с Halda: • 70B Q4K → Halda распределяет: D1 GPU 20 слоёв, D2 GPU 12, D3 GPU 15, D4 CPU 10+disk → Прогноз: 400–600 мс/токен → 1.7–2.5 tok/s → С speculative decoding: 3–5 tok/s • QwQ-32B → D1 GPU вмещает целиком → Halda: только D1 → ~15–20 tok/s (CUDA на RTX 4060 Ti) → С speculative decoding: 30+ tok/s
Это лучший сценарий для prima.cpp! Гетерогенный кластер из б/у десктопов с NVIDIA GPU — именно то, для чего prima.cpp создан. Halda оптимально распределяет нагрузку между разными GPU и CPU. $1 550 за кластер, запускающий 70B модели на 2–5 tok/s — лучше, чем Mac Mini M4 Pro ($2 199) на тех же моделях.

Сценарий C: Смешанный Mac + PC кластер

Кластер: D1: Mac Mini M4 (16 ГБ, Metal) $599 D2: Мини-ПК с RTX 4060 (8 ГБ VRAM, 32 ГБ RAM) $600 D3: Старый ноутбук (CPU-only, 16 ГБ RAM) $0 Сеть: Gigabit Ethernet Итого: ~$1 200 prima.cpp: • 70B Q4K → D1 Metal + D2 CUDA + D3 CPU → PRP с prefetching → Прогноз: 500–800 мс/токен → 1.2–2 tok/s → Halda учитывает, что Metal медленнее CUDA → даёт D1 меньше слоёв Сравнение с альтернативами: • EXO на том же кластере: не работает (нет RDMA, разные ОС) • llama.cpp RPC: ~3000+ мс/токен (pipeline, без disk offloading) • distributed-llama: не поддерживает GPU → prima.cpp = единственный рабочий вариант для этого микса

Только CUDA GPU Критическое Vulkan «в роадмапе». AMD ROCm и Intel OneAPI — не упоминаются
Ограниченный список моделей Существенное Поддерживаются: Llama 3, Qwen 2.5, QwQ, DeepSeek R1. Только Q4KM, Q6K, Q80 квантизации
Минимум 1 слой на устройство Среднее Для малых моделей — overhead. Планируют исправить (0:0:32:0 splits)
Нет MoE-специфичных оптимизаций Незначительное MoE-модели (Qwen3-30B-A3B, DeepSeek V3) работают, но без sparse inference оптимизаций
Нет Windows Существенное для мини-ПК Linux, macOS, Android, HarmonyOS. Многие мини-ПК идут с Windows → нужно ставить Linux
Молодой проект Риск Статья — апрель 2025, GitHub — активная разработка, но community ещё маленькое
Memory pressure от других приложений Незначительное mmap делит память с ОС — если запустить тяжёлое приложение, инференс замедлится
Speculative decoding требует 2 модели Незначительное Для 26 tok/s на 32B нужна маленькая draft-модель + основная. Больше RAM/VRAM
Главная проблема для типичного кластера мини-ПК: Большинство мини-ПК (Strix Halo, Mac Mini, Intel NUC, Minisforum без dGPU) работают с prima.cpp только на CPU. CPU-only prima.cpp всё равно быстрее llama.cpp на моделях 30B+ благодаря PRP, но без CUDA GPU — значительная часть потенциала теряется. Vulkan-поддержка — самое ожидаемое обновление, которое откроет AMD и Intel GPU для prima.cpp.

8. 🛠️ Установка и настройка prima.cpp

Требования

На каждом узле: Linux (Ubuntu 20+) или macOS. GCC/Clang, cmake, make, git. Для GPU: CUDA toolkit. Для оптимального планирования: HiGHS ILP solver.

Пошаговая установка

# === На каждом узле кластера === # 1. Установить HiGHS (оптимизатор для Halda) git clone https://github.com/ERGO-Code/HiGHS.git cd HiGHS mkdir build && cd build cmake .. make -j$(nproc) sudo make install cd ../.. # 2. Клонировать prima.cpp git clone https://github.com/Lizonghang/prima.cpp.git cd prima.cpp # 3. Собрать (с HiGHS для Halda) make USE_HIGHS=1 -j$(nproc) # Если есть NVIDIA GPU: make USE_HIGHS=1 GGML_CUDA=1 -j$(nproc) # Если macOS с Metal: make USE_HIGHS=1 GGML_METAL=1 -j$(nproc)

Запуск кластера

# === Настройка сети (статические IP) === # Мастер: 192.168.1.100 # Worker1: 192.168.1.101 # Worker2: 192.168.1.102 # Worker3: 192.168.1.103 # === На каждом worker-узле === cd prima.cpp ./prima-server --port 8888 # === На мастер-узле === # Скачать модель (GGUF формат) wget https://huggingface.co/.../llama-3-70b-Q4_K_M.gguf # Запуск с Halda (автоматическое профилирование и распределение) ./prima-cli \ --model llama-3-70b-Q4_K_M.gguf \ --workers 192.168.1.101:8888,192.168.1.102:8888,192.168.1.103:8888 \ --prompt "Explain quantum computing in simple terms" \ --n-predict 256

9. 📋 Итоговое сравнение всех фреймворков для мини-ПК

Фреймворк Параллелизм Disk offload GPU Гетерогенность 70B на слабом кластере 70B на мощном кластере
prima.cpp PRP (кольцо) ✅ mmap CUDA, Metal Отличная 1.5 tok/s 3–8 tok/s (прогноз)
EXO TP (macOS RDMA) ❌ Metal, MLX Только Mac N/A (нужно RAM≥модель) 32 tok/s (4×Mac Pro)

Когда какой фреймворк использовать

prima.cpp ✅ Когда выбирать

• Кластер из разнородных устройств (Mac + PC + ноутбук + телефон)
• Модель не влезает в суммарную RAM кластера
• Есть хотя бы один узел с NVIDIA GPU
• Нужна низкая memory pressure (устройства используются для другого)
• Модели 30B–70B — зона максимального преимущества
• Wi-Fi соединение (единственный фреймворк, оптимизированный для медленных сетей)

EXO ✅ Когда лучше

• Кластер из Mac Mini M4 Pro (однородный)
• Thunderbolt 5 RDMA доступен
• Модель влезает в суммарную RAM
• Нужна максимальная скорость (tensor parallelism + RDMA = непобедимо)
• Только macOS устройства

llama.cpp RPC ✅ Когда лучше

• Нужна поддержка AMD GPU (ROCm) или Intel (SYCL)
• Один мощный узел + помощники
• Модель влезает в RAM одного узла (RPC не нужен)
• Самая зрелая и стабильная кодовая база

distributed-llama ✅ Когда лучше

• Кластер из одинаковых SBC (Raspberry Pi 5)
• MoE модели (Qwen3-30B-A3B) — специально оптимизирован
• Нужен tensor parallelism на ARM CPU
• Ультрабюджет ($585 за 4×Pi5)

10. 🎯 Вердикт: что меняет prima.cpp для мини-ПК кластеров

prima.cpp — это game-changer для гетерогенных домашних кластеров

До prima.cpp: Если у вас 2 ноутбука, десктоп и телефон с суммарно 30 ГБ свободной RAM — запустить 70B модель было невозможно. llama.cpp на одном устройстве давал ~0.03 tok/s (30 секунд на токен). EXO не работал на смешанных ОС. distributed-llama — OOM.

С prima.cpp: Те же устройства → 1.5 tok/s на 70B. QwQ-32B → 11 tok/s. Со speculative decoding → 26 tok/s на 32B. Memory pressure <6% — устройства продолжают нормально работать.

Для кластеров мини-ПК: практические рекомендации

✅ Идеальный сценарий: Кластер из 2–4 б/у десктопов/мини-ПК с NVIDIA GPU (RTX 2080Ti / 3070 / 4060) + Gigabit Ethernet. Стоимость: $1000–2000. Результат: 70B модели на 2–5 tok/s, 32B на 15–26 tok/s. Лучшее соотношение цена/производительность для домашнего LLM-кластера в 2026 году.
✅ Хороший сценарий: «Собери что есть дома» — Mac Mini + ноутбук + старый ПК + телефон. prima.cpp — единственный фреймворк, который объединит всё это в рабочий кластер. Даже через Wi-Fi. Результат зависит от железа, но 70B на 1–2 tok/s реалистично.
⚠️ Ограниченный сценарий: Кластер из мини-ПК без NVIDIA GPU (Framework Desktop, Mac Mini, Intel NUC). prima.cpp работает CPU-only. На моделях ≤RAM одного узла — нет преимущества. На моделях >RAM — PRP + disk offloading всё равно лучше llama.cpp RPC, но без GPU-ускорения скорость будет 0.5–2 tok/s на 70B.
❌ Когда prima.cpp хуже:
• Маленькие модели (≤14B) — overhead от распределения. Используйте llama.cpp/Ollama на одном устройстве.
• Однородный Mac-кластер — EXO с TB5 RDMA даёт 32 tok/s на 70B. prima.cpp не может конкурировать с RDMA tensor parallelism.
• Модели, которые влезают в RAM одного узла — просто используйте llama.cpp. prima.cpp добавляет overhead без пользы.

Финальная мысль: prima.cpp заполняет огромную нишу, которую не покрывал ни один другой фреймворк: запуск больших моделей на слабом, разнородном железе с недостаточной RAM. Для кластеров мини-ПК с NVIDIA GPU — это лучший выбор. Для кластеров без NVIDIA GPU — ждём Vulkan. Для однородных Mac-кластеров — EXO всё ещё король.
